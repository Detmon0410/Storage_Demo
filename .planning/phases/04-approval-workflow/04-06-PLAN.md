<objective>
Bring the two order-management pages back in sync with the Phase 4 backend field split, AND give the
approval workflow its first (and only) UI entry point: remove the now-nonfunctional free-text
`approver` inputs (approval is server-side and automatic per D-04/D-05 — there is no "type an
approver name to bypass a warning" flow anymore), rename the Import Orders page's status field/filter
to the new `logisticsStatus`, surface the real approval `status` (including `REJECTED` with its
`rejectionReason`) as a read-only display on both tables, AND add Approve/Reject buttons on
`PENDING_APPROVAL` rows that call the real `POST /:id/approve` and `POST /:id/reject` endpoints
(reject requires typing a reason). Before this plan, no button/action/API call anywhere in the
frontend could trigger approve/reject — the only way to exercise APPROVAL-06 was a direct API call.
This plan closes that gap.

Purpose: `SalesOrdersPage.tsx`'s client-side `needsApproval` gate currently blocks form submission
based on a free-text `approver` field the user types into — this duplicated, now-obsolete
client-side logic must be removed since the backend auto-routes to PENDING_APPROVAL regardless of
what the client sends. `ImportOrdersPage.tsx`'s `status` field/filter must follow the backend rename
or the page will send an invalid/rejected field to the API. And since APPROVAL-06's success criterion
("a user holding Manager/Approver permission can approve or reject a pending order") must be reachable
by an actual human user, not just curl/Postman, this plan adds the minimal UI trigger: buttons gated
client-side (UX only) by the same permission the backend already enforces server-side.
Output: Updated types.ts, resources.ts (approval API calls), both order pages (status display +
approve/reject buttons), status.ts tone mapping, and both locale files.
</objective>
