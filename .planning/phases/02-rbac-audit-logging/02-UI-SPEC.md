# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none (same hand-rolled Tailwind v4 component set from `apps/frontend/src/components/ui/`, established in Phase 1) |
| Preset | not applicable |
| Component library | none (reuse existing primitives: `Button`, `Field`/`TextInput`/`SelectField`/`CheckboxField`, `FormGrid`, `Card`, `Badge`, `DataTable`, `Modal`, `ConfirmDialog`, `PageHeader`, `SearchInput`, `States` (`LoadingState`/`ErrorState`/`EmptyState`), `Toast`) |
| Icon library | `lucide-react` (existing dependency) — new icons needed for this phase: `UserCog` (Users nav item — `Users` is already used by the Customers nav entry, so a distinct icon avoids sidebar ambiguity), `ScrollText` (Audit Log nav item), `ShieldCheck` (role badges, optional inline use), `RotateCcw` (reactivate action) |
| Font | `"Segoe UI", "Noto Sans Thai", system-ui, -apple-system, sans-serif` (unchanged, `--font-sans` in `apps/frontend/src/index.css`) |

**Decision rationale:** Per CONTEXT.md D-03, this phase explicitly reuses the existing CRUD table+modal pattern (Suppliers/Products/Customers) with no new component library and no new visual language. No `components.json` exists in this repo (confirmed absent again for this phase); Phase 1 already made the "no shadcn, extend the hand-rolled system" call and nothing about this phase's two screens changes that calculus. Proceeding without re-asking the shadcn question, consistent with `01-UI-SPEC.md`'s precedent.

## Spacing Scale

Unchanged from Phase 1 — reused, not re-derived:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding (badge icon gap, role-chip gap) |
| sm | 8px | Compact spacing (checkbox-to-label gap in role picker, filter-bar gap) |
| md | 16px | Default element spacing (`gap-4` FormGrid, filter row `gap-2`→`gap-3` wraps at this scale) |
| lg | 24px | Section padding (`mb-6` PageHeader, modal internal padding) |
| xl | 32px | Layout gaps (space between filter bar and table on Audit Log page) |
| 2xl | 48px | Major section breaks (not used within these two screens — no full-page empty/loading centering taller than the existing `py-16` pattern) |
| 3xl | 64px | Page-level spacing (not used — both screens are table-first, not single-card layouts) |

Exceptions:
- Role checkbox grid (User modal): use `gap-2` (8px) between individual role checkboxes, matching existing `CheckboxField` label gap (`gap-2` inside the component) — do not introduce a new spacing value for this.
- Audit log filter bar: 4 filter controls (entity, user, action, date range) sit in `PageHeader`'s existing `filters` slot, which already applies `flex flex-wrap items-center gap-2` — no override needed.

Unchanged from Phase 1 — no new sizes or weights introduced:

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 (regular) | 1.5 |
| Label | 12px (`text-xs`) | 400 (regular) | 1.5 |

## Color

Unchanged palette — reused, not re-derived. No new hues introduced.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `slate-50` (#f8fafc) page background / `white` table & modal surface | Page background, `DataTable` surface, `Modal` surface (existing `AppShell` background, unchanged) |
| Secondary (30%) | `slate-200`/`slate-300` (#e2e8f0 / #cbd5e1) | Table borders, input borders, card dividers — plus **role chips** (inactive/unselected role badges use `bg-slate-100 text-slate-600`, matching existing `Badge` `neutral` tone) |
| Accent (10%) | `amber-600` (#d97706) | Primary "Create user" / "Apply filters" buttons, input focus rings, active sidebar nav item (Users, Audit Log), selected-role checkbox fill (`CheckboxField`'s existing `text-amber-600` checked state — already built, reused as-is) |
| Destructive | `rose-600` (#e11d48) / `rose-500` text | Deactivate-user action icon + confirmation dialog only. **Not** used for the reject action (reject uses `warning`/`amber` tone per below) or for reactivate (uses `success`/`emerald` tone) |

Two additional semantic tones are needed for this phase's status badges — both already exist in `Badge`'s `TONE_CLASSES` map (`lib/status.ts` `Tone` type), no new colors introduced:
- **Active user** → `success` tone (`emerald-50`/`emerald-700`) — reuses existing `Badge tone="success"`, same as `ACTIVE` supplier/product status today.
- **Inactive/deactivated user** → `neutral` tone (`slate-100`/`slate-600`) — reuses existing `Badge tone="neutral"`, same as `INACTIVE` status today. Do NOT use `danger`/rose for a deactivated user — deactivation is a routine admin action, not an error state, and rose is reserved for destructive-action affordances (buttons/icons) per the Phase 1 contract, not passive status display.
- **Audit action type badges** (create/update/delete/login/logout/approve/reject/export) reuse existing tones: `create`→`success` (emerald), `update`→`info` (sky), `delete`→`danger` (rose), `login`/`logout`→`neutral` (slate), `approve`→`success` (emerald), `reject`→`warning` (amber), `export`→`info` (sky).

Accent reserved for: the primary "Create user" button, "Apply filters" button (if audit log filters require an explicit apply step rather than live-filtering — see Interaction Notes), input/select/date-range focus rings, the active state of the new "Users" and "Audit Log" sidebar nav items, and the checked-state fill of role-assignment checkboxes. Never used for role-chip backgrounds, status badges, or table row backgrounds.

**Role badge colors (new pattern for this phase — 6 roles, each needs a stable identifying color so a user's multi-role chip row is scannable at a glance):**

| Role Code | Display Label | Badge Tone |
|-----------|---------------|------------|
| `SYSTEM_ADMIN` | System Admin | `danger` (rose) — signals highest-privilege role, deliberately visually distinct/cautionary |
| `MANAGER_APPROVER` | Manager / Approver | `warning` (amber) |
| `IMPORT_COMPLIANCE_OFFICER` | Import & Compliance Officer | `info` (sky) |
| `WAREHOUSE_DISTRIBUTION_OFFICER` | Warehouse & Distribution Officer | `neutral` (slate) |
| `SALES_OFFICER` | Sales Officer | `success` (emerald) |
| `FINANCE_ACCOUNTING_OFFICER` | Finance / Accounting Officer | `info` (sky, same as Import & Compliance — acceptable since both are secondary/back-office roles rarely co-displayed as a scanning-conflict pair; do not introduce a 7th tone) |

This reuses the existing 5-tone `Badge` system exactly as-is (`success`/`warning`/`danger`/`info`/`neutral`) — no new tone values added to `lib/status.ts`. A user with multiple roles renders one `Badge` per role, wrapped (`Badge wrap` prop already supports this), in a `flex flex-wrap gap-1` row within the table cell and in the modal's read context.

## Interaction & State Notes (phase-specific)

Not part of the template's core sections but required for executor clarity given RBAC-01..06 and AUDIT-01..04:

**Multi-role assignment UX (the phase's main new interaction surface):**
- Render the 6 roles as a `FormGrid`-contained block (not individual `Field`-wrapped inputs) using six `CheckboxField` instances (existing component, already styled with `text-amber-600` checked fill) in a 2-column grid (`grid grid-cols-1 gap-2 sm:grid-cols-2`) inside the create/edit user Modal, spanning the modal's full width (`colSpan={2}` equivalent — use a wrapping `<div className="sm:col-span-2">` around the checkbox grid since `FormGrid`'s children are meant to be `Field`s, not raw divs).
- Each checkbox label is the role's display label (see role table above), not the raw code — codes are internal only, never shown to the admin user.
- No "select all" convenience control — 6 roles is small enough that a select-all adds more visual noise than it saves clicks (matches this project's minimalist admin-UI precedent).
- Roles field is required: block submit and show the `user.toastRolesRequired` toast if zero roles are checked, mirroring the existing `product.toastSelectRequired` pattern for required cross-entity selections.
- In the Users table (list view), render assigned roles as wrapped `Badge` chips (per Color section above) in a dedicated "Roles" column — do not truncate to "+N more"; wrap the row height instead (`DataTable` already supports variable row height via its existing `align-middle` cell styling).

**Users page layout (mirrors SuppliersPage.tsx exactly):**
- `PageHeader` with `filters={<SearchInput .../>}` (search by username) and `actions={<Button variant="primary" icon={<Plus/>}>Add user</Button>}`.
- `DataTable` columns: Username, Roles (badge row), Status (badge), Actions (edit pencil + deactivate/reactivate toggle icon — `Trash2` is NOT used here since this is not a delete operation; use `UserX`/`UserCheck` or `Ban`/`RotateCcw` icon pairs to visually distinguish deactivate-vs-delete semantics from Suppliers/Products' hard-delete pattern).
- Create/Edit `Modal` at `width="max-w-lg"` (default, no need for Product's wider `max-w-2xl` — fewer fields than Product).
- No password field on edit (only shown on create) — editing a user's password is out of scope for this phase's screen (not listed in D-03's create/edit/deactivate/reactivate scope); a future "reset password" action is not part of this contract.

**Audit Log page layout (new pattern, not a 1:1 copy of the CRUD pages since it has no create/edit/delete actions):**
- `PageHeader` title "Audit Log", subtitle as above, `filters` slot contains 4 controls in a row (Entity select, User select, Action select, Date-range pair) using the same `flex flex-wrap gap-2` wrapping the existing `PageHeader` filters slot already provides — no `actions` slot content (omit the `actions` prop entirely, do not pass an empty node).
- Filters apply live (on-change, debounced client-side filter of already-fetched rows) if the expected data volume is small enough for one page-load fetch; if audit volume requires server-side pagination/filtering (a research-phase decision, not a UI-SPEC decision), the same visual filter bar applies — only the data-fetching trigger (live vs. an explicit "Apply" button) changes. Default to live client-side filtering unless RESEARCH.md for this phase says otherwise; if server-side filtering is chosen, add an explicit "Apply filters" `Button variant="secondary" size="sm"` at the end of the filter row (accent-colored per the Color section) rather than silently refetching on every keystroke.
- `DataTable` columns: Timestamp, User, Action (badge), Entity, Entity ID, Details (ghost "View details" button opening the before/after modal described in Copywriting).
- Table rows are read-only — no row-level edit/delete affordance of any kind (AUDIT-03: no UI path may ever suggest an audit entry is editable). Do not reuse the Actions-column edit-pencil pattern from other CRUD pages; the only per-row action is the non-destructive "View details" viewer.
- Sort order: newest-first (descending timestamp) by default, matching typical audit-log UX expectations; no user-facing sort control needed for this phase (single fixed sort is sufficient per D-04's simple binary-access scope).

**Navigation (Sidebar/Topbar):**
- Add "Users" (`UserCog` icon) and "Audit Log" (`ScrollText` icon) as new items. Per D-04, Audit Log is visible only to `SYSTEM_ADMIN`/`MANAGER_APPROVER`; per RBAC-05, Users management is `SYSTEM_ADMIN`-only. Add both to a new `nav.group.administration` group in `NAV_GROUPS` (`nav.ts`), positioned last (after `nav.group.sales`), so admin-only items are visually separated from the operational modules rather than interleaved.
- Nav visibility must be conditional on the current user's role/permission — this requires `AuthContext` to carry the user's roles/permissions (currently it only carries `{ id, username }`, no role data). This is a functional/data requirement for the planner and executor, not a visual one: the UI-SPEC's contract is that when a `NavItem` has a `requiresRole`/`requiresPermission` field (new optional field on the `NavItem` interface), `Sidebar.tsx` filters it out of `NAV_GROUPS` rendering for users lacking that role — same visual treatment (no greyed-out/disabled state) as items simply not existing, since exposing hidden functionality even in a disabled state on an audit/user-management surface is an unnecessary information leak.
- Sidebar item styling for the two new items is unchanged from existing nav items (active state `bg-amber-50 text-amber-700`, inactive `text-slate-600 hover:bg-slate-50`) — no visual distinction needed to mark them "admin-only" since access-gating already handles that; adding a visual "admin" badge on the nav item itself would be redundant and clutter the sidebar.
