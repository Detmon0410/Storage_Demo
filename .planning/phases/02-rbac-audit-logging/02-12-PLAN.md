<objective>
Give the frontend visibility into the logged-in user's roles/permissions (needed by plans 02-13 and
02-14's UI, and by nav-gating), via a new `GET /api/auth/me` endpoint built on the same
`RoleModel.getUserPermissionCodes`/`getUserRoleCodes` queries plan 02-02 already built for
`requirePermission` — reused here, not reimplemented. Extend `AuthContext` to fetch this after both
`login()` and the existing silent-refresh `useEffect` (page reload case), since `/auth/refresh`
does not return user identity today (documented gap in the existing code's own comment). Add nav
gating so the Users/Audit Log sidebar items are hidden (not disabled) for users lacking the relevant
permission, per `02-UI-SPEC.md`'s explicit "no greyed-out state" requirement.

Purpose: RBAC-03 (union-of-roles semantics must be visible/consumable) and RBAC-06 (frontend must
reflect live, DB-derived permissions, not a stale login-time snapshot) both need this endpoint to
exist before the Users/Audit Log pages (plans 02-13/02-14) can be built.
Output: `/api/auth/me` endpoint, extended `AuthContext`, nav gating wired into `Sidebar.tsx`.
</objective>

    ```typescript
    import { RoleModel } from "../models/role.model.js";

    export const me = asyncHandler(async (req: AuthenticatedRequest, res) => {
      const user = await UserModel.findById(req.userId!);
      if (!user) throw new HttpError(404, "User not found");
      const [roles, permissions] = await Promise.all([
        RoleModel.getUserRoleCodes(user.id),
        RoleModel.getUserPermissionCodes(user.id),
      ]);
      res.json({ id: user.id, username: user.username, roles, permissions: Array.from(permissions) });
    });
    ```

    ```typescript
    async function fetchMe(token: string): Promise<AuthUser | null> {
      const res = await fetch(`${BASE_URL}/auth/me`, { headers: { Authorization: `Bearer ${token}` } });

    }
    ```

    logged-in state, do not force logout for this edge case, just fall back to `null` user as today).
    In `login()`, after `applyToken(data.accessToken, data.user)` (where `data.user` is still only
    `{ id, username }` from `/auth/login`'s response, unchanged by this plan), immediately call
    `fetchMe(data.accessToken)` and re-apply the fuller user object via `applyToken(data.accessToken, fullUser)`
    if it succeeds — this means `login()` now does two round-trips (login + me), which is acceptable
    since it only happens once per session start, not per-request.
